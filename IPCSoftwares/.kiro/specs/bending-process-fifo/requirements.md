# Requirements Document

## Introduction

This document defines the requirements for a FIFO-based batch process tracking system for a 9-stage bending machine. The system manages batch lifecycle from QR code scanning at the input position through bending, tearing, flipping, and final inspection at the output position. A new `Bending_Process.cs` file in `IPCSoftware.CoreService.Bending\Service\` will implement the process logic, integrating with the existing `DashboardInitializerBase` 500ms processing loop and PLC tag infrastructure.

## Glossary

- **Batch**: A group of exactly 4 parts that flow together through all 9 stages of the bending machine
- **FIFO_Queue**: A first-in-first-out data structure that tracks the order and position of up to 9 active batches across all stages
- **Batch_Number**: A unique identifier generated by the Core_Service for each batch, formatted as `BN-YYYYMMDD-NNN` where NNN is a daily sequential counter
- **Core_Service**: The `IPCSoftware.CoreService.Bending` background service that processes PLC data and manages the bending workflow
- **Stage**: One of 9 physical positions in the bending machine where a batch can reside
- **TT1**: Turn Table 1, a 4-position rotary table (90° per step) holding batches at Stages 2, 3, 4, and 5
- **TT2**: Turn Table 2, a 3-position rotary table (120° per step) holding batches at Stages 6, 7, and 8
- **Transfer_Module**: The mechanism that moves a batch from TT1 Position 4 (Stage 5) to TT2 Position 1 (Stage 6)
- **PLC**: Programmable Logic Controller that provides trigger signals and process data via Modbus tags
- **Dashboard_Table**: A scrollable UI table displaying all active batch states (up to 9 rows) with Stage 9 data shown at the top
- **Robot_1**: The robot at the input side that scans QR codes and places batches onto TT1
- **Robot_2**: The robot at the output side that picks batches from TT2 and places them at the inspection position
- **Bending_Process_Service**: The new service class (`Bending_Process.cs`) responsible for FIFO tracking and stage transition logic
- **DashboardInitializerBase**: The base class providing the 500ms processing loop and `latestValueNew` dictionary for PLC tag values

## Requirements

### Requirement 1: Batch Creation on Robot Pick Completion

**User Story:** As a production operator, I want the system to automatically create a new batch when Robot-1 completes QR scanning, so that every set of 4 parts is tracked from entry.

#### Acceptance Criteria

1. WHEN the PLC signal `Robot_Pick_Done` transitions from false to true, THE Bending_Process_Service SHALL create a new Batch with a unique Batch_Number and store the 4 scanned QR codes read from the configured PLC tag IDs in the `latestValueNew` dictionary
2. THE Bending_Process_Service SHALL generate Batch_Number in the format `BN-YYYYMMDD-NNN` where YYYYMMDD is the current date and NNN is a zero-padded daily sequential counter starting at 001, resetting to 001 at the start of each new calendar day
3. WHEN a new Batch is created, THE Bending_Process_Service SHALL enqueue the Batch at the tail of the FIFO_Queue with its Stage set to 1
4. IF the FIFO_Queue already contains 9 batches, THEN THE Bending_Process_Service SHALL reject the new batch creation, log a warning message indicating the queue is full, and discard the incoming batch data without altering the existing queue state
5. IF any of the 4 QR code values is empty or null at the time of `Robot_Pick_Done` rising edge, THEN THE Bending_Process_Service SHALL reject the batch creation and log a warning message indicating which QR code position (1-4) was invalid
6. IF the daily sequential counter exceeds 999, THEN THE Bending_Process_Service SHALL continue incrementing the counter beyond 3 digits (e.g., 1000) without rejecting batch creation

### Requirement 2: FIFO Queue Management

**User Story:** As a system architect, I want a FIFO queue that tracks batch positions across all 9 stages, so that the system always knows which batch is at which physical position.

#### Acceptance Criteria

1. THE FIFO_Queue SHALL maintain an ordered collection of active batches with a maximum capacity of 9, where each position in the queue corresponds to a unique Stage (no two batches may occupy the same Stage simultaneously)
2. THE FIFO_Queue SHALL track for each Batch: the Batch_Number, current Stage number (1-9), 4 QR codes, process data collected at each stage (as defined by the Batch model), and inspection result
3. WHEN a Batch advances from one Stage to the next, THE Bending_Process_Service SHALL update the Batch Stage number in the FIFO_Queue; IF multiple stage transitions are triggered within the same 500ms processing cycle, THEN THE Bending_Process_Service SHALL process all triggered transitions in order from highest Stage number to lowest Stage number
4. WHEN a Batch completes Stage 9 (data logging is complete per Requirement 7), THE Bending_Process_Service SHALL dequeue the Batch from the FIFO_Queue head
5. THE FIFO_Queue SHALL preserve insertion order so that the oldest Batch is always at the head
6. WHEN the Bending_Process_Service starts or restarts, THE Bending_Process_Service SHALL initialize the FIFO_Queue as empty, requiring batches to be re-introduced from Stage 1

### Requirement 3: TT1 Stage Transitions (Stages 2-5)

**User Story:** As a production operator, I want batches to advance through Turn Table 1 positions automatically based on PLC signals, so that the process flows without manual intervention.

#### Acceptance Criteria

1. WHEN the PLC signal `Robot_Pick_Done` transitions from false to true and Stage 2 is unoccupied, THE Bending_Process_Service SHALL advance the Batch from Stage 1 to Stage 2
2. WHEN the PLC signal `TT1_Index_Complete` transitions from false to true and Stage 3 is unoccupied, THE Bending_Process_Service SHALL advance the Batch from Stage 2 to Stage 3
3. WHEN the PLC signals `CD_B1_ALL_DATA_READ_COMP` and `CD_B2_ALL_DATA_READ_COMP` both transition from false to true at Stage 3, THE Bending_Process_Service SHALL record 8 Temperature values (4 from Bending-1, 4 from Bending-2) and 8 Load values (4 from Bending-1, 4 from Bending-2) for the Batch
4. WHEN the PLC signal `TT1_Index_Complete` transitions from false to true and Stage 4 is unoccupied, THE Bending_Process_Service SHALL advance the Batch from Stage 3 to Stage 4
5. WHEN the PLC signal `CD_B3_ALL_DATA_READ_COMP` transitions from false to true at Stage 4, THE Bending_Process_Service SHALL record 4 Temperature, 4 Load, 4 X, 4 Y, 4 Z, and 4 W values for the Batch
6. WHEN the PLC signal `TT1_Index_Complete` transitions from false to true and Stage 5 is unoccupied, THE Bending_Process_Service SHALL advance the Batch from Stage 4 to Stage 5
7. IF a TT1 stage transition is triggered but the target Stage is occupied by another Batch, THEN THE Bending_Process_Service SHALL not advance the Batch and SHALL retain the Batch at its current Stage until the target Stage becomes unoccupied
8. WHILE a Batch is at Stage 3 awaiting bending completion, THE Bending_Process_Service SHALL NOT advance the Batch to Stage 4 until both `CD_B1_ALL_DATA_READ_COMP` and `CD_B2_ALL_DATA_READ_COMP` signals have been received and the corresponding process data has been recorded

### Requirement 4: Transfer Module Transition (Stage 5 to Stage 6)

**User Story:** As a production operator, I want the transfer module to move batches from TT1 to TT2 seamlessly, so that the production flow continues without interruption.

#### Acceptance Criteria

1. WHEN the PLC signal `Transfer_Done` transitions from false to true and Stage 6 is unoccupied, THE Bending_Process_Service SHALL advance the Batch from Stage 5 to Stage 6
2. WHILE the Transfer_Module is active (PLC signal `Transfer_Active` is true), THE Bending_Process_Service SHALL prevent TT1 from rotating to Stage 5 with a new batch
3. IF the PLC signal `Transfer_Done` transitions from false to true and Stage 6 is occupied, THEN THE Bending_Process_Service SHALL not advance the Batch and SHALL log a warning message

### Requirement 5: TT2 Stage Transitions with Shared Signal (Stages 6-8)

**User Story:** As a system architect, I want the FIFO logic to determine batch positions on TT2 using a single shared rotation signal, so that the system correctly tracks batches despite the shared trigger.

#### Acceptance Criteria

1. WHEN the PLC signal `TT2_Start` transitions from false to true, THE Bending_Process_Service SHALL advance all batches currently on TT2 by one position (Stage 6→7, Stage 7→8), processing the highest-stage batch first to prevent position conflicts
2. IF the PLC signal `TT2_Start` transitions from false to true and Stage 8 is occupied by a Batch that has not been picked by Robot_2, THEN THE Bending_Process_Service SHALL not advance any TT2 batches and SHALL log a warning
3. THE Bending_Process_Service SHALL use FIFO_Queue order to determine which Batch occupies which TT2 position, without relying on per-position PLC signals
4. WHILE a Batch is at Stage 6, WHEN the PLC signal indicating Tearing process completion transitions from false to true, THE Bending_Process_Service SHALL record 4 Temperature values for the Batch from the configured PLC tag IDs
5. WHILE a Batch is at Stage 7, WHEN the PLC signal indicating Flipping process completion transitions from false to true, THE Bending_Process_Service SHALL record 4 Force values for the Batch from the configured PLC tag IDs
6. THE Bending_Process_Service SHALL allow a Batch to advance from Stage 6 to Stage 7 or from Stage 7 to Stage 8 regardless of whether process data recording has completed for that stage

### Requirement 6: Robot-2 Pick and Output (Stage 8 to Stage 9)

**User Story:** As a production operator, I want Robot-2 to pick completed batches from TT2 and place them at the inspection station, so that final quality checks can be performed.

#### Acceptance Criteria

1. WHEN the PLC signal `Robo2_Done` transitions from false to true and Stage 9 is unoccupied, THE Bending_Process_Service SHALL advance the Batch currently at Stage 8 to Stage 9
2. IF the PLC signal `Robo2_Done` transitions from false to true and no Batch is currently at Stage 8, THEN THE Bending_Process_Service SHALL ignore the signal and log a diagnostic message
3. IF the PLC signal `Robo2_Done` transitions from false to true and Stage 9 is occupied, THEN THE Bending_Process_Service SHALL not advance the Batch and SHALL log a warning message
4. WHEN a Batch arrives at Stage 9, THE Bending_Process_Service SHALL write the inspection start signal to the PLC to initiate the camera inspection process within the same 500ms processing cycle

### Requirement 7: Final Inspection and Data Logging (Stage 9)

**User Story:** As a quality engineer, I want the system to capture camera inspection results and log all batch data at Stage 9, so that I have a complete production record for each batch.

#### Acceptance Criteria

1. WHEN the PLC signal for camera inspection completion transitions from false to true at Stage 9, THE Bending_Process_Service SHALL read the OK or NG result for each of the 4 parts from the configured PLC tag IDs and record them in the Batch
2. WHEN all 4 part inspection results are recorded, THE Bending_Process_Service SHALL persist the complete Batch data (Batch_Number, QR codes, all process data from Stages 3-7, and inspection results) to the historical data log within 5 seconds
3. WHEN data logging completes successfully for a Batch, THE Bending_Process_Service SHALL dequeue the Batch from the FIFO_Queue head
4. IF persistence to the historical data log fails, THEN THE Bending_Process_Service SHALL retain the Batch in the FIFO_Queue, log a diagnostic message, and retry persistence on the next 500ms processing cycle up to a maximum of 5 attempts
5. IF the camera inspection result is not available within 10 seconds of the Batch arriving at Stage 9, THEN THE Bending_Process_Service SHALL log a warning and continue waiting without blocking other stage transitions

### Requirement 8: Dashboard Display of Active Batches

**User Story:** As a production operator, I want to see all active batch states on the dashboard simultaneously, so that I can monitor the entire production line at a glance.

#### Acceptance Criteria

1. THE Bending_Process_Service SHALL expose a model containing all active Batch states (up to 9 rows) for the Dashboard_Table, where each row includes the Batch_Number, current Stage number, and process data collected so far
2. THE Dashboard_Table SHALL display rows sorted with Stage 9 batches positioned at the top, followed by remaining batches in descending Stage order (Stage 8 before Stage 7, and so on)
3. WHILE the Dashboard_Table contains more rows than fit within the visible table viewport, THE Dashboard_Table SHALL provide vertical scrolling to access all rows
4. WHEN a Batch Stage or process data changes, THE Bending_Process_Service SHALL update the corresponding Dashboard_Table row within the next 500ms processing cycle
5. IF the FIFO_Queue contains zero active batches, THEN THE Dashboard_Table SHALL display an empty table with no data rows

### Requirement 9: Process Data Model Structure

**User Story:** As a developer, I want well-defined models for batch and process data, so that the UI and service layers share a consistent data contract.

#### Acceptance Criteria

1. THE Batch model SHALL contain: Batch_Number (string, max 16 characters), Stage (integer 1-9), QR codes (4 strings, max 256 characters each), Bending-1 data (4 Temperatures as float, 4 Loads as float), Bending-2 data (4 Temperatures as float, 4 Loads as float), Bending-3 data (4 Temperatures as float, 4 Loads as float, 4 X as float, 4 Y as float, 4 Z as float, 4 W as float), Tearing data (4 Temperatures as float), Flipping data (4 Forces as float), and Inspection results (4 booleans)
2. THE Batch model SHALL reside in the `IPCSoftware.Shared\Models\Bending\` namespace and inherit from ObservableObjectVM
3. THE Bending_Process_Service SHALL reside in `IPCSoftware.CoreService.Bending\Service\Bending_Process.cs`
4. THE Bending_Process_Service SHALL read PLC tag values from the `latestValueNew` dictionary (Dictionary<int, object>) which is populated by the existing 500ms processing loop in DashboardInitializerBase
5. WHEN a new Batch is created, THE Batch model SHALL initialize all numeric process data fields to 0f, all QR code fields to empty string, Stage to 1, and all Inspection result fields to false

### Requirement 10: PLC Tag Integration

**User Story:** As a developer, I want the process logic to read PLC signals from the existing tag infrastructure, so that the FIFO system reacts to real machine events.

#### Acceptance Criteria

1. THE Bending_Process_Service SHALL read all trigger signals (`Robot_Pick_Done`, `TT2_Start`, `Robo2_Done`, TT1 rotation signals) from the `latestValueNew` dictionary using PLC tag IDs configured in the `appsettings.json` TagMapping section and loaded via the ConstantValues static class
2. THE Bending_Process_Service SHALL read all process data values (Temperatures, Loads, X, Y, Z, W) from the `latestValueNew` dictionary as floating-point numbers, using PLC tag IDs configured in the `appsettings.json` TagMapping section and loaded via the ConstantValues static class
3. THE Bending_Process_Service SHALL use placeholder tag IDs (integer value of 0) for signals not yet defined by the PLC engineer, and SHALL skip processing for any signal whose configured tag ID equals 0
4. IF a configured PLC tag ID with a non-zero value is not present as a key in the `latestValueNew` dictionary, THEN THE Bending_Process_Service SHALL skip processing for that signal and log a diagnostic message containing the missing tag ID and the signal name
5. IF a PLC tag value is present in the `latestValueNew` dictionary but cannot be parsed to the expected data type (boolean for triggers, float for process data), THEN THE Bending_Process_Service SHALL treat the value as the type default (false for boolean, 0.0 for float) and continue processing

### Requirement 11: Stage Transition Edge Detection

**User Story:** As a system architect, I want the system to detect rising edges on PLC trigger signals, so that a single PLC pulse triggers exactly one stage transition.

#### Acceptance Criteria

1. THE Bending_Process_Service SHALL detect rising edges (false-to-true transitions) on all trigger signals (`Robot_Pick_Done`, `TT2_Start`, `Robo2_Done`, and TT1 rotation signals) by comparing current values against previously stored values
2. WHEN a rising edge is detected on a trigger signal, THE Bending_Process_Service SHALL execute the corresponding stage transition exactly once, regardless of how many consecutive processing cycles the signal remains true
3. THE Bending_Process_Service SHALL store the previous state of each trigger signal between processing cycles
4. WHEN the Bending_Process_Service starts or restarts, THE Bending_Process_Service SHALL initialize all previous trigger signal states to true so that signals already high at startup do not produce a spurious rising edge
5. IF a rising edge is detected but the corresponding stage transition precondition is not met (e.g., target stage is occupied), THEN THE Bending_Process_Service SHALL discard the edge event and log a diagnostic message without retrying on subsequent cycles
